# ADR-013. Стратегия тестирования: семантика, падения, гонки

- Статус: принято автором 2026-10-26
- Дата: 2026-10-26

## Контекст

На каждом этапе — тесты, включая сценарии: убить процесс посреди шага,
повторная доставка события, гонка двух воркеров, неизвестный исход
неповторяемого шага.

## Решение

Пять слоёв.

### 1. Семантика интерпретатора (ядро, чистые функции)

- Табличные тесты `step(definition, snapshot, event) → (snapshot', commands, journal)`
  без хранилища.
- Набор по мотивам W3C SCXML IRP (порядок exit/enter, выбор переходов в
  иерархии, конфликты в параллельных регионах, `done.state`, history,
  eventless до стабилизации, лимит микрошагов) — адаптированные сценарии,
  не прямой порт.
- Валидатор определений: отрицательные случаи по каждому правилу.

### 2. Харнесс падений (ядро, детерминированно)

`FaultInjector` с именованными точками в рантайме:

```
runner.before_commit         runner.after_commit_before_dispatch
effect.after_claim           effect.after_call_before_record
effect.after_record          ticker.after_fire_before_inbox
reconcile.after_call         migration.mid_apply
```

Тест «убивает процесс» в точке (исключение `SimulatedCrash`, все
незакоммиченные изменения in-memory UoW отбрасываются, аренда остаётся
висеть), затем продвигает виртуальные часы за TTL аренды, запускает
sweeper и рантайм заново и проверяет **инварианты**:

- I1: каждое событие inbox обработано ровно один раз (по журналу);
- I2: `idempotent`-обработчик вызван ≥ 1 раза на ключ, процесс получил
  ровно один `done`;
- I3: `at-most-once`-обработчик вызван ≤ 1 раза на ключ; после падения
  в `effect.after_claim`/`after_call_before_record` — статус `unknown`,
  повторных вызовов нет, открыт инцидент либо отработала сверка;
- I4: снапшот согласован с журналом (свёртка `context_patch` = контекст);
- I5: нет потерянных таймеров (каждый `pending` либо сработал, либо
  отменён после выхода из активации).

Перебор: для эталонных процессов — **все** точки × все шаги
(параметризованный тест), а не выборочно.

### 3. Гонки (ядро — симуляция, мост — по-настоящему)

- Ядро: детерминированный планировщик чередует операции двух «воркеров»
  по заданному расписанию (захват аренды, шаг, фиксация) — перебор
  чередований для коротких сценариев: две доставки одного события,
  два воркера на один экземпляр, «зомби» с истёкшей арендой фиксирует
  после перехвата (fencing отбивает), отмена таймера vs срабатывание.
- Laravel-слой: реальные процессы (`pcntl_fork` / Symfony Process) против
  PostgreSQL и MySQL (в CI сервисами) и SQLite (WAL); N воркеров ×
  M событий × K экземпляров, проверка тех же инвариантов I1–I5. Убийство
  — `posix_kill(SIGKILL)` воркера посреди шага/эффекта.

### 4. Сквозные сценарии

Эталонный процесс «урегулирование убытка» ([`../reference-scenario.md`](../reference-scenario.md))
— в `tests/Scenarios/` ядра (in-memory, виртуальные часы) и моста
(БД + очередь `sync`/`database`): счастливый путь, три дозапроса подряд,
таймаут подписи, отказ стороны, `unknown` при выплате → сверка → ручное
решение, отмена клиентом с компенсацией, миграция v1→v2 в середине.

### 5. Контракт экспорта

Экспорт во flow валидируется JSON-схемами flow (ADR-012); снапшоты
эталонного сценария — golden-файлы.

### Инструменты

Pest (как в delayed-process), Pest arch-тесты на чистоту ядра, phpstan
level 5 (ядро стремимся к level 8 — новое, долга нет), pint. CI-матрица
по канону: PHP 8.2–8.5 × Laravel 11/12/13 (для моста), ядро — PHP 8.2–8.5.

## Последствия

- Рантайм с самого начала пишется с точками инъекции и абстракцией часов
  — без этого харнесс не построить задним числом.
- Харнесс (`FaultInjector`, виртуальные часы, `EngineTestCase`) — часть
  публичного API ядра: пользователи тестируют свои процессы тем же.
