# ADR-004. Модель исполнения: шаг, inbox/outbox, блокировки, воркеры

- Статус: предложено
- Дата: 2026-10-26

## Контекст

Процесс живёт неделями, между шагами в памяти ничего нет (R2). После падения
процесс поднимается с последней зафиксированной точки, двойного выполнения
нет (R3). Источники пробуждения: внешнее событие, таймер, результат эффекта,
результат дочернего процесса, ручная операция.

## Решение

### 1. Шаг = чистая функция + одна транзакция

```
step(definition, snapshot, event, now) → (snapshot', commands[], journal[])
```

- `Interpreter::step` — **чистая** функция ядра: без БД, без часов (время
  шага `now` передаётся аргументом и пишется в журнал), без вызова эффектов.
- Внутри — макрошаг SCXML: выбор переходов по событию → exit/transition/entry
  действия → eventless-переходы и внутренние события (`raise`, `done.state.*`)
  до стабилизации (микрошаги). Защита от зацикливания: лимит микрошагов
  (по умолчанию 100) → шаг отклоняется, инцидент `microstep_limit`.
- `commands[]` — что сделать во внешнем мире: `ScheduleEffect`,
  `CancelEffect`, `StartTimer`, `CancelTimer`, `Subscribe`/`Unsubscribe`
  (корреляция), `StartChild`, `CancelChild`, `NotifyParent`, `Compensate`.
- Рантайм применяет результат **в одной транзакции БД**: снапшот (с проверкой
  версии), журнал, строки outbox/таймеров/подписок, отметка «событие
  обработано» в inbox. Либо всё, либо ничего.

### 2. Всё входящее — через inbox

Любое пробуждение — строка `inbox` с полями `instance_id`, `name`, `payload`,
`actor`, `idempotency_key`, `received_at`, `processed_at`, `seq`
(монотонный порядок поступления в пределах экземпляра).

- Уникальный индекс `(instance_id, idempotency_key)` — повторная доставка
  того же события вставкой отбивается, отправитель получает «уже принято»
  (ADR-010). Ключ задаёт отправитель; для внутренних событий движок выводит
  его детерминированно (`timer:<id>`, `effect:<id>:done`, `child:<id>:done`).
- Порядок обработки — FIFO по `seq` в пределах экземпляра.
- Событие, которое текущая конфигурация не принимает: по умолчанию
  `ignored` (запись в журнал «почему проигнорировано»); если состояние
  объявило `defer: [event]` — остаётся в inbox до конфигурации, которая его
  примет (или до TTL).

### 3. Эффекты — через outbox, после фиксации

Шаг только создаёт строку `effects` (`pending`). Исполнение — отдельно
(ADR-006):

```
txn A: effects.pending → running (attempt+1, lease)   [commit]
       вызов обработчика (вне транзакции, вне блокировки экземпляра)
txn B: effects.running → succeeded|failed + inbox(done/error-событие)  [commit]
```

Результат эффекта возвращается в процесс **событием через inbox** — значит,
переход по результату идёт тем же путём, что и любое событие, с той же
идемпотентностью. Эффекты разных экземпляров и даже одного экземпляра
(параллельные регионы) исполняются параллельно; блокировка экземпляра на
время вызова не держится.

### 4. Блокировка экземпляра: аренда + fencing

Обработка inbox экземпляра строго последовательна.

- **Аренда:** `UPDATE instances SET locked_by=:worker, lease_until=:now+ttl
  WHERE id=:id AND (lease_until IS NULL OR lease_until < :now)`; затронута
  0 строк — экземпляр занят, джоб завершается (его событие подхватит
  владелец аренды, он вычерпывает inbox до конца).
- **Fencing через версию снапшота:** фиксация шага —
  `UPDATE … SET seq = seq + 1 … WHERE id=:id AND seq=:expected`. Если аренда
  истекла и экземпляр перехватил другой воркер, «зомби» получит 0 строк,
  откатит транзакцию и выйдет. Это защищает даже от длинной паузы GC/сети,
  при которой аренда истекла незаметно для владельца.
- Портируемо на PostgreSQL, MySQL 8 и SQLite (без `SKIP LOCKED` и
  advisory locks). `SELECT … FOR UPDATE SKIP LOCKED` — оптимизация выборки
  кандидатов в sweeper на PG/MySQL, не механизм корректности.
- Внешний `Cache::lock` не используется: второй источник истины о владении.

### 5. Кто крутит колёса

| Компонент | Что делает | Как запускается (Laravel-слой) |
|---|---|---|
| `InstanceRunner` | берёт аренду, вычерпывает inbox, шаг за шагом | джоб `RunInstance(id)`, диспатч после commit |
| `EffectExecutor` | захватывает эффект, вызывает обработчик, пишет результат | джоб `ExecuteEffect(id)`, диспатч после commit |
| `TimerTicker` | переводит наступившие таймеры в события inbox | `process-engine:tick` по расписанию каждую минуту; опционально демон `process-engine:work` с секундной точностью |
| `Sweeper` | самолечение: протухшие аренды, зависшие `running`-эффекты, необработанные события без джоба, эффекты с наступившим `next_attempt_at` | тот же `tick` |

**Очередь — только «дверной звонок», не источник истины.** Потерянный джоб
не теряет работу: sweeper найдёт необработанную строку inbox / pending-эффект
и передиспатчит. Поэтому подходит любой драйвер очереди, включая `sync`
и `database`; длинные задержки (недели) не кладутся в очередь — они живут
в таблице таймеров.

### 6. Синхронный режим

`Engine` можно крутить без очереди: `send()` сразу выполняет шаги, эффекты
исполняются инлайн, пока есть работа (`drain()`). Используется в тестах,
CLI и простых приложениях. Семантика та же; отличается только транспорт.

### 7. Гарантии (контракт движка)

- **Переходы — ровно один раз на событие inbox** (дедупликация + атомарная
  фиксация + fencing).
- **Эффекты `idempotent` — минимум один раз** (повтор при сомнении).
- **Эффекты `at-most-once` — не больше одного вызова на ключ**; при сомнении —
  статус `unknown`, без автоповтора (ADR-006).
- **Порядок событий экземпляра** — порядок поступления в inbox.
- Между экземплярами порядок не гарантируется.

## Последствия

- Обработчики эффектов получают ключ идемпотентности и должны передавать его
  во внешние системы, где это возможно (Idempotency-Key платёжных API).
- Задержка «событие → переход» — время доставки джоба (или до минуты, если
  джоб потерян и спас sweeper).
- Пропускная способность одного экземпляра ограничена последовательной
  обработкой — для процессов «человеческого темпа» это не ограничение;
  массовая параллельность — через дочерние процессы (ADR-009).

## Отвергнутые альтернативы

- **Исполнять эффекты внутри транзакции шага.** Длинные транзакции,
  а главное — откат транзакции не откатывает внешний мир: двойное списание
  после падения между вызовом и commit.
- **Отложенные джобы очереди как таймеры.** Ограничения драйверов (SQS — 15
  минут), потеря при сбросе очереди, невозможность отменить/перечислить.
- **Pessimistic `SELECT … FOR UPDATE` на всё время шага.** Работает, но
  держит соединение и строку; на SQLite неприменимо; аренда + fencing
  дают то же без долгих блокировок.
