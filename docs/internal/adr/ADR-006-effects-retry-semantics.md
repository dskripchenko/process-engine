# ADR-006. Эффекты: семантика повтора, неизвестный исход, компенсации, инциденты

- Статус: принято автором 2026-10-26
- Дата: 2026-10-26

## Контекст

R4: у каждого действия явно задана семантика повтора — повторяемое
(повторная отправка договора на печать), неповторяемое (списание средств:
при неизвестном исходе — состояние «неизвестно», без автоповтора; сверка,
компенсация или ручное решение), компенсируемое (saga). Плюс политики
повторов: число попыток, backoff, что делать по исчерпании.

## Решение

### 1. Семантика — обязательный атрибут эффекта

Семантика объявляется **атрибутом на классе эффекта** (`#[Idempotent]`,
`#[AtMostOnce]`): это свойство самого побочного действия, а не места его
вызова в графе ([client-api.md](../client-api.md)). Класс эффекта без атрибута
не принимается: определение с таким эффектом не пройдёт валидацию.
Умолчания нет сознательно, автор процесса должен подумать. Определение
может переопределить только политику повторов, но не семантику.

| Семантика | Гарантия | Поведение при сомнении |
|---|---|---|
| `idempotent` | ≥ 1 вызова | повторить по политике |
| `at-most-once` | ≤ 1 вызова на ключ | `unknown`, без автоповтора |
| `compensable` | как `idempotent` или `at-most-once` (указывается `base`) + есть обработчик отката | см. базовую; откат по команде `compensate` |

`compensable` — не третья ось повтора, а свойство «есть откат»: класс
реализует интерфейс `Compensable` (метод `compensate()`) и при этом
объявляет одну из двух семантик повтора. Сверка — интерфейс `Reconcilable`
(метод `reconcile()`).

### 2. Ключ идемпотентности эффекта

`key = <instance_id>/<state>@<activation>/<effect_id>[#<n>]` — детерминирован:
повторный вход в то же состояние (цикл дозапросов) даёт новый ключ, повтор
попытки — тот же. Обработчик получает его в `EffectContext::idempotencyKey()`
и обязан передавать во внешнюю систему, если она это поддерживает.
(В клиентском API — `Effect::$key`.)

### 3. Классификация исхода обработчика

Обработчик (invokable-класс, аргументы подставляются по типу: контекст,
`Effect`) завершается так:

| Исход | Как сообщается | Смысл |
|---|---|---|
| успех | возврат значения (JSON-сериализуемого) | `succeeded`, событие `done` |
| `NotExecuted` | исключение `EffectNotExecuted` | точно не выполнилось (не дошли до внешней системы) — повтор безопасен для любой семантики |
| `Failed` | исключение `EffectFailed(code, details)` | точно выполнилось с отказом (бизнес-ошибка: «недостаточно средств») — не повторяется, событие `error` с кодом |
| прочее | любое другое исключение, таймаут, падение воркера | **неоднозначно** |

Неоднозначный исход: для `idempotent` — повтор по политике; для
`at-most-once` — **`unknown`**.

В атрибуте можно указать `retryOn`/`nonRetryable` (класс исключения или
код ошибки) — это уточняет повторы для `idempotent`.

### 4. Механика at-most-once

```
txn A: status=running, attempt=1, started_at, lease_until   [commit]  ← отметка «начато»
call handler
txn B: status=succeeded|failed, result, inbox event          [commit]
```

- Падение между A и B → sweeper находит `running` с истёкшей арендой →
  `unknown` (не `pending`!).
- Повторная доставка джоба на эффект в статусе `running`/`unknown` —
  no-op: захват идёт только из `pending`.
- `unknown` порождает событие `unknown.invoke.<id>` (или `unknown.effect.<id>`)
  и, если определение его не обрабатывает, **инцидент** `effect_unknown`.

### 5. Сверка (reconcile)

У эффекта можно объявить `reconciler` — идемпотентное чтение внешней
системы по ключу:

```
ReconcileOutcome::succeeded($result) | failed($code) | notExecuted() | stillUnknown()
```

- Запускается автоматически при переходе в `unknown` с собственной
  политикой повторов (по умолчанию: 10 попыток, экспонента 1 мин → 6 ч).
- `succeeded`/`failed` — эффект закрывается, процесс получает обычное
  `done`/`error`, как будто вызов вернулся.
- `notExecuted` — эффект возвращается в `pending` **одноразово** и
  исполняется снова (обработчику уходит тот же ключ).
- `stillUnknown` по исчерпании — инцидент; решает человек (ADR-011:
  `resolveEffect(succeeded|failed|retry)` с обязательной причиной).

### 6. Политики повторов (как данные)

```json
{
  "maxAttempts": 5,
  "initialInterval": "PT10S",
  "backoffCoefficient": 2.0,
  "maxInterval": "PT1H",
  "jitter": "full",
  "attemptTimeout": "PT2M",
  "nonRetryable": ["insufficient_funds"],
  "onExhausted": "error"
}
```

- `onExhausted`: `error` — событие `error.invoke.<id>` с кодом
  `retries_exhausted` (определение решает, куда идти; не обработано →
  инцидент), `incident` — сразу инцидент, процесс ждёт оператора,
  `fail` — экземпляр в `failed`.
- Умолчания: `idempotent` — 5 попыток, 10 с → 1 ч, `onExhausted: error`;
  `at-most-once` — повторяются только `EffectNotExecuted`, до 3 раз.
- Именованные политики регистрируются глобально (`policies.default`,
  `policies.external-api`) и подставляются по имени.
- `attemptTimeout` — аренда эффекта; PHP не прерывает вызов, поэтому таймаут
  — это граница, после которой sweeper считает попытку оборвавшейся
  (для `at-most-once` → `unknown`). Laravel-слой выставляет `timeout`
  джоба меньше аренды.

### 7. Компенсации (saga)

- Эффект `compensable` объявляет `compensate: handler` (+ своя семантика,
  обычно `idempotent`, и политика: по умолчанию «до победного», потом
  инцидент).
- **Область компенсации** — состояние с флагом `saga: true` (любой
  составной) или весь процесс.
- Действие `compensate(scope?)` (из перехода, обычно по `error`/`cancel`)
  планирует откат **успешно завершённых** compensable-эффектов области в
  обратном порядке завершения, последовательно. По окончании — событие
  `done.compensation.<scope>`; сбой отката после политики — инцидент
  `compensation_failed`.
- Эффект в `unknown` внутри области блокирует компенсацию: сначала сверка
  или ручное решение (иначе можно «вернуть» несписанные деньги).
- Отмена экземпляра (`cancel(compensate: true)`) = компенсация всего
  процесса + `cancelled`.

### 8. Отмена эффектов при выходе из состояния

Выход из состояния с активным `invoke` (переход по таймауту, `join: any`
в параллельном):
- `pending` → `cancelled`;
- `running idempotent` → результат после возврата записывается в журнал как
  «осиротевший», в процесс не идёт;
- `running at-most-once` → результат записывается; если исход `unknown` —
  инцидент всё равно поднимается (деньги важнее того, что процесс ушёл
  дальше); для `compensable` можно объявить `onOrphan: compensate`.

### 9. Инциденты

Объект первого класса (`pe_incidents`): `effect_exhausted`, `effect_unknown`,
`compensation_failed`, `microstep_limit`, `unhandled_error`,
`handler_missing`, `context_too_large`, `migration_failed`. Экземпляр с
открытым инцидентом помечен `has_incidents`, остальные регионы продолжают
работу. Разрешение — только ручной операцией с актором и причиной (ADR-011).

## Последствия

- Обработчик эффекта — единственное место, где разработчик решает «точно не
  выполнилось / точно отказ / не знаю». Документация даёт рецепты для
  HTTP-клиентов (ошибка соединения до отправки → `NotExecuted`; таймаут
  чтения → неоднозначно).
- Fire-and-forget эффекты в `entry` (уведомление клиенту) не влияют на
  переходы, но подчиняются той же семантике и политике.

## Отвергнутые альтернативы

- **Умолчание `idempotent`.** Ровно та ошибка, ради которой R4: списание,
  объявленное без раздумий, будет повторено.
- **Автоповтор `at-most-once` после сверки «не найдено».** Только через
  явный `notExecuted` от сверки — «не нашли» у многих API значит «ещё не
  видно».
