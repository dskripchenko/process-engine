# ADR-001. Позиционирование и отношение к laravel-delayed-process

- Статус: предложено (ждёт согласования автора)
- Дата: 2026-10-26

## Контекст

У автора есть `dskripchenko/laravel-delayed-process` (актуальный тег 2.2.0
от 2026-10-02; в постановке упомянут 2.1.2 — 2.2.0 его заменяет, API тот же).
Нужно решить: новый движок развивает этот пакет, использует его как способ
исполнения шагов или идёт независимо.

Что такое delayed-process по коду (`src/Services/DelayedProcessRunner.php`,
`src/Models/DelayedProcess.php`):

- единица — **один вызов** `entity::method(parameters)` в фоне через джоб;
  результат в `data`, логи в `logs`, прогресс 0–100, `callback_url`;
- статусы `new → wait → done | error | expired | cancelled`;
- захват строки атомарным `UPDATE … WHERE status='new'`; повтор при ошибке —
  возврат статуса в `new`, пока `try < attempts` (то есть **любой** сбой
  автоматически повторяется);
- allowlist сущностей в конфиге; JS-модуль для фронта — авто-поллинг по
  конверту `{payload:{delayed:{uuid,status}}}`;
- команды `delayed:process|clear|unstuck|expire`.

Это хороший пакет для своей задачи: «длинный HTTP-запрос → фоновое
выполнение + поллинг с фронта».

## Решение

**Движок идёт независимо** и не использует delayed-process как исполнитель
шагов. Взаимодействие — через **необязательный мост** (этап 7):

1. эффект-обработчик `DelayedProcessHandler`: шаг процесса запускает delayed
   process и ждёт его завершения; слушатели `ProcessCompleted`/`ProcessFailed`
   превращают его в событие движка `done/error` для этого эффекта
   (идемпотентный ключ — uuid delayed process);
2. ответ HTTP-ручки движка может отдаваться в конверте delayed-process,
   чтобы существующий фронт автора опрашивал шаг процесса без доработок.

delayed-process **не меняем** (ни сейчас, ни ради моста): мост живёт
на стороне движка и опирается только на публичные события и модель 2.x.

## Обоснование

1. **Разная единица работы.** У delayed-process единица — вызов функции,
   у движка — экземпляр процесса из многих шагов с графом, контекстом,
   ожиданиями и таймерами. Втаскивание графа в delayed-process ломает его
   простую модель и 2.x-контракт.
2. **Конфликт семантики повтора.** Runner повторяет любой сбой. Требование R4
   прямо запрещает автоповтор неповторяемого шага при неизвестном исходе и
   требует состояния «неизвестно». Пришлось бы либо менять семантику пакета
   (ломающая правка для текущих пользователей), либо обходить её флагами.
3. **Два источника истины.** Если шаг — строка `delayed_processes`, а
   процесс — строка движка, то атомарность «шаг выполнен ⇔ процесс сделал
   переход» требует распределённой фиксации между двумя таблицами с разными
   правилами захвата. Движку нужен собственный outbox эффектов с ключом
   идемпотентности, привязанным к активации состояния (ADR-004, ADR-006).
4. **Нужное движку отсутствует в пакете:** ключ идемпотентности шага,
   отметка «начато» до вызова для неповторяемых эффектов, сверка
   (reconcile), компенсации, backoff на уровне строки, таймеры на недели,
   корреляция внешних событий.
5. **Мост даёт пользу без связности:** существующие обработчики
   delayed-process можно вызывать из процесса, фронт автора может опрашивать
   шаги процесса.

## Последствия

- Код захвата/повтора частично похож на delayed-process (атомарный claim,
  `unstuck`) — это осознанное дублирование идеи, не кода.
- В README движка — раздел «когда delayed-process, а когда process-engine».
- Мост — опциональный: `suggest` в composer Laravel-слоя, без жёсткой
  зависимости.

## Отвергнутые альтернативы

- **Развивать delayed-process до движка (3.0).** Ломает простой пакет,
  смешивает две задачи, тянет миграцию существующих пользователей.
- **delayed-process как транспорт исполнения шагов.** См. п. 2–3: семантика
  повторов и два источника истины.
