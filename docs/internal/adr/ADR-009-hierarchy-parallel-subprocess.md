# ADR-009. Иерархия, параллельные ветки, подпроцессы

- Статус: принято автором 2026-10-26
- Дата: 2026-10-26

## Контекст

R1: вложенные подпроцессы (иерархия), параллельные ветки с ожиданием всех
или любой. Пример: после согласования параллельно согласуются форма
компенсации и время/место техобслуживания; дозапросы документов — цикл,
иногда несколько дозапросов одновременно.

## Решение

Два механизма с разной ценой — выбирает автор процесса.

### 1. Внутри одного экземпляра: составные и параллельные состояния

- **Составное** (`compound`) — иерархия любой глубины, общий контекст,
  общий журнал. Переходы, объявленные на предке, действуют во всех
  потомках (например, `on: client.cancelled` на корне или `after: P30D`
  на этапе как «граничный таймер» всего этапа).
- **Параллельное** (`parallel`) — регионы активны одновременно; каждый
  регион — составное состояние со своим финалом.
  - `join: all` (по умолчанию, SCXML): `done.state.<parallel>` когда все
    регионы в финале.
  - `join: any`: первый регион в финале → `done.state.<parallel>`,
    остальные регионы выходят (exit-действия, отмена `invoke` по ADR-006 §8).
  - `join: {quorum: n}` — позже, если появится сценарий.
- Регионы обрабатываются **логически параллельно, физически
  последовательно** (одна аренда на экземпляр, ADR-004); эффекты регионов
  исполняются по-настоящему параллельно.
- `output` финала региона мёрджится в `done`-событие параллельного
  состояния (`event.output.<regionId>`).
- **History** (`shallow`/`deep`) — возврат в последнюю конфигурацию
  составного (например, «приостановить этап на ручную проверку и вернуться
  туда же»).

### 2. Отдельный экземпляр: дочерний процесс (`invoke: process`)

```php
->invoke(DocumentRequest::class,                // a class that extends Process
         input: $this->requestInput(...),         // parent context → child input
         onDone: 'awaitingParty', onError: '…')
```

- Дочерний экземпляр — полноценный: своя версия определения, свой
  контекст, журнал, аренда; `parent_id` + `parent_invoke`.
- Версия дочернего фиксируется **в момент запуска** (по умолчанию —
  последняя на тот момент; `pinned` — версия, указанная в определении
  родителя).
- Завершение ребёнка → событие `done.invoke.<id>` (с `output`) /
  `error.invoke.<id>` в inbox родителя, ключ идемпотентности
  `child:<child_id>:done`.
- Выход родителя из состояния-владельца → отмена ребёнка (каскадно);
  отмена с компенсацией — по флагу.
- Ребёнок не видит контекст родителя: только `input`; наружу — только
  `output`. Это граница инкапсуляции.

### 3. Множественные экземпляры (`forEach`)

`->invoke(DocumentRequest::class, forEach: 'documentRequests')` — N детей по
элементам коллекции, `join: all | any`, результаты собираются в
`event.output[]` в порядке коллекции. Аналог Map из Step Functions
и multi-instance из BPMN. Для «несколько дозапросов одновременно».

### 4. `forEach` для эффектов (G3)

`->invoke(AttachDocument::class, forEach: 'documents', into: 'uploaded', concurrency: 5)`
— N эффектов по элементам коллекции, `join: all`. Ключ i-го эффекта —
`<key>#<i>`, он стабилен. Обработчик получает элемент через `Effect::$item`
и `Effect::$index`. Результаты складываются в список по порядку
коллекции. Если элемент упал после политики повторов, весь `invoke`
получает `error`. Успешные элементы при повторе оператором не
перевыполняются: их ключи уже закрыты. `concurrency` ограничивает число
одновременных вызовов (по умолчанию без ограничения).

### 5. Дочерний процесс на событие — `spawn` (G6)

`->on(NotificationReceived::class, spawn: ClaimRequest::class, input: $this->requestInput(...), key: 'messageId')`

- На каждое событие создаётся дочерний экземпляр, без перехода родителя.
- Время жизни ребёнка — **область, где объявлен `spawn`**: состояние (пока
  оно активно) или корень (пока жив процесс). При выходе из области
  незавершённые дети отменяются (`onScopeExit: cancel`, по умолчанию) или
  остаются жить (`keep`).
- `key` — поле события. Повтор с тем же ключом нового ребёнка не создаёт:
  ключ идемпотентности `spawn:<parent>:<value>`.
- Завершение ребёнка присылает родителю `done.spawn.<childName>`
  (с `output` и ключом). Реагировать на него не обязательно.
  `StepContext::spawned()` даёт число живых детей, например для guard
  «закрыть, когда открытых запросов нет».

### 6. Маршрутизация по финалу ребёнка (G4)

У дочернего процесса бывает несколько финалов (подпись: `signed` /
`refused` / `expired`). `done.invoke` несёт id финала и `output`.
Билдер раскладывает `onDone: [final => target]` в переходы
(ADR-007). Ребёнок, упавший с ошибкой (инцидент без решения или
`fail`), присылает `error.invoke`.

### Когда что

| Нужно | Механизм |
|---|---|
| этапы одного процесса, общий контекст, переходы «из любого места этапа» | составное состояние |
| одновременные ветки, которые синхронизируются | параллельное состояние |
| переиспользуемый кусок процесса в разных процессах, своя версия, свой жизненный цикл | дочерний процесс |
| N однотипных веток по данным | `forEach` дочерних процессов |
| N однотипных внешних вызовов по данным | `forEach` эффектов |
| заранее неизвестное число параллельных подпроцессов, приходящих событиями | `spawn` |
| очень высокая параллельность внутри процесса | дочерние процессы (разные аренды) |

## Последствия

- Экспорт во flow: составное и параллельное — узлы с `subgraph` (drill-down),
  дочерний процесс — узел `subprocess` со ссылкой на определение ребёнка
  (ADR-012).
- «Где сейчас» для родителя включает ссылки на активных детей и их состояние.

## Отвергнутые альтернативы

- **Только дочерние процессы (без parallel внутри экземпляра).** Дороже
  для частого случая «две ветки и join», дробит журнал.
- **Только parallel (без детей).** Нет переиспользования и независимого
  версионирования кусков; нет динамического числа веток.
