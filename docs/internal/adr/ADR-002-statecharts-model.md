# ADR-002. Модель процесса: statecharts с явным графом

- Статус: принято автором 2026-10-26
- Дата: 2026-10-26

## Контекст

Три семейства моделей (подробно — [`../research/landscape.md`](../research/landscape.md)):

1. **Durable execution / код как процесс** (Temporal, Durable Workflow) —
   процесс пишется кодом, состояние восстанавливается воспроизведением.
2. **BPMN / токены** (Camunda, Zeebe) — графическая нотация с токенной
   семантикой.
3. **Statecharts** (Harel, SCXML, XState) — иерархическая машина состояний
   с контекстом.

Жёсткие требования, которые различают модели: ручной перевод в состояние
(R7), отрисовка определения и положения во flow без адаптера (E1),
версионирование с доживанием старых экземпляров (R5), иерархия и
параллельные регионы (R1).

## Решение

Модель движка — **statechart с явным сериализуемым графом**, семантика шага —
по алгоритму SCXML (W3C), с расширениями для долгоживущего исполнения.

### Узлы (state nodes)

| Тип | Смысл |
|---|---|
| `atomic` | лист; в нём экземпляр «стоит» |
| `compound` | составной: дочерние состояния, `initial`; иерархия любой глубины |
| `parallel` | регионы, активные одновременно; `join: all \| any` (позже `quorum: n`) |
| `final` | финал составного/параллельного/процесса; порождает `done.state.<id>` с `output` |
| `choice` | псевдосостояние: только `always`-переходы с guards (ветвление) |
| `history` | псевдосостояние `shallow \| deep` — возврат в последнюю конфигурацию региона |

У любого состояния: `entry[]`, `exit[]`, `on{event: transition[]}`,
`always[]`, `after{delay: transition[]}`, `invoke[]`, `defer[]`, `tags[]`,
`meta{}` (произвольные данные для UI/экспорта, ядро их не читает).

### Переходы

`{event?, guard?, actions[], target?, internal?}`. Без `target` — внутренний
(самопереход без выхода). Без `event` — eventless (`always`). Выбор —
SCXML: от самого глубокого активного состояния вверх, первый в порядке
документа, чей guard истинен; конфликтующие переходы в параллельных регионах
разрешаются по SCXML.

### Действия

Три класса, различие принципиально (см. ADR-004, ADR-006):

1. **Чистые** — выполняются внутри шага, без ввода-вывода:
   `assign` (изменение контекста), `raise` (внутреннее событие),
   `log` (запись в журнал), `startTimer`/`cancelTimer` (декларативно,
   таймеры — строки хранилища).
2. **Эффекты** (`effect`) — побочные действия во внешнем мире; внутри шага
   только **планируются** (outbox), исполняются после фиксации шага с явной
   семантикой повтора: `idempotent | at-most-once | compensable`.
3. **Деятельности состояния** (`invoke`) — эффект или дочерний процесс,
   живущий, пока активно состояние; результат приходит событиями
   `done.invoke.<id>` / `error.invoke.<id>` / `unknown.invoke.<id>`;
   при выходе из состояния — отмена.

Guards и чистые действия обязаны быть детерминированными и без
ввода-вывода: им доступны только контекст, событие и «время шага» (ADR-004).

### Контекст

JSON-сериализуемый массив (`array<string, mixed>`), хранится в снапшоте.
Крупные данные (файлы, сформированные документы) — по ссылке, хранит хост.
Лимит размера контекста — настройка (по умолчанию 256 КБ, превышение —
ошибка шага → инцидент).

### Ожидание внешнего (R2)

Не отдельный тип узла, а следствие модели: атомарное состояние без `always`
и без активных `invoke` с синхронным исходом — это **ожидание**. Экземпляр
в нём ничего не держит в памяти; проснётся от события из inbox, срабатывания
таймера `after`/дедлайна или результата `invoke`.

## Обоснование

- **Явный граф** = определение можно сериализовать, хранить по версиям,
  рисовать во flow напрямую (ADR-012), вычислять «какие события сейчас
  ожидаются», проверять статически (достижимость, тупики).
- **Перевод в состояние** — штатная операция над конфигурацией (выйти из
  текущих, войти в целевые), а не хак над стеком вызовов.
- **Версионирование** проще, чем в replay-модели: экземпляр привязан
  к снапшоту определения, а не к коду, который обязан воспроизводиться
  детерминированно (ADR-008).
- **SCXML даёт готовую формальную семантику** шага: не изобретаем порядок
  exit/enter и разрешение конфликтов, есть набор тестов-идей W3C IRP.
- Иерархия и параллельность statecharts напрямую покрывают «многоуровневый
  процесс с параллельными ветками».

## Последствия

- Логика процесса — граф + именованные обработчики; «код процесса» в духе
  Temporal не поддерживается. Для линейных кусков с ветвлением есть `choice`
  и компактный DSL (ADR-007).
- Движок реализует свою версию алгоритма SCXML на PHP — это центральная
  и самая тестируемая часть ядра (ADR-013).
- Из SCXML сознательно **не берём**: `<script>`/ECMAScript datamodel,
  `<send>` во внешние I/O-процессоры (заменено эффектами), `<donedata>`
  в полном виде (у нас `output` финала).

## Отвергнутые альтернативы

- **Durable execution (код).** Нет явного графа (E1), нельзя перевести
  в состояние (R7), версионирование через ветки в коде на годы.
- **BPMN.** Тяжёлый формат, токенная семантика избыточна, нет готового
  встраиваемого PHP-исполнителя; flow всё равно рисует не BPMN.
- **Плоская FSM (symfony/workflow, spatie).** Нет иерархии и
  параллельности; эмуляция разрастается комбинаторно.
