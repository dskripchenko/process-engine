# ADR-010. Внешние события и таймеры

- Статус: принято автором 2026-10-26
- Дата: 2026-10-26

## Контекст

R2: шаг «засыпает» до события (ввод клиента, ответ стороны, callback) или
до таймера/дедлайна. Реальность асинхронных сторон: ответ может прийти
дважды, раньше, чем процесс начал его ждать, или после того, как процесс
ушёл дальше.

## Решение

### 1. Адресация события

Внешнее событие доставляется одним из способов:

| Способ | Когда | Как |
|---|---|---|
| по `instance_id` | отправитель знает экземпляр (наша же форма клиента) | `engine->send($instanceId, Event::named('form.submitted', $payload)->key($messageId)->by($actor))` |
| по корреляции | внешняя сторона знает только свой номер (номер заявки у страховщика) | `engine->publish('party.decision', correlationKey: 'APP-123', …)` |
| по токену задачи | callback конкретному шагу (как `waitForTaskToken`) | токен = подписанный идентификатор активации; `engine->complete($token, $payload)` |

**Корреляция:** состояние объявляет
`correlate('party.decision', by: '$.context.application.externalId')`.
При входе в состояние создаётся строка `pe_subscriptions`
(`event`, `correlation_key`, `instance_id`, `activation`), при выходе —
удаляется. `publish` находит подписчиков; нет подписчика — сообщение
кладётся в **буфер** `pe_messages` с TTL (умолчание — настройка, например
P7D) и доставляется, как только появится подписка (Zeebe-модель). Это
закрывает гонку «сторона ответила раньше, чем мы начали ждать».

**Токен задачи:** HMAC(`instance_id`, `state@activation`, `secret`) — его
можно отдать внешней стороне в callback URL; устаревшая активация →
событие отклоняется с внятной ошибкой.

### 2. Дедупликация

- Ключ идемпотентности обязателен для внешних событий (`key()`); без
  ключа движок генерирует случайный и пишет предупреждение в журнал
  (повторная доставка такого события не распознается).
- Повтор с тем же ключом → `Accepted::duplicate($originalReceipt)`, без
  новой строки inbox. Для `publish` дедуп — по `(event, correlation_key,
  key)` в буфере и в inbox.

### 3. Валидация payload

Событие может объявить валидатор по имени (`validate: 'claim.form'`):
вызывается **до записи в inbox** синхронно у отправителя — клиент сразу
получает ошибки формы, а в процесс не попадает мусор. Ядро не знает форм:
валидатор — реализация хоста (JSON Schema, Laravel Validator, что угодно).

### 4. Событие, которое сейчас не ждут

- По умолчанию — `ignored` с записью в журнал: имя, текущая конфигурация,
  «ожидались: …». Отправитель получает `Accepted` (событие принято,
  но может быть проигнорировано) — асинхронный ответ не зависит от гонок.
- Синхронный режим «принять, только если сейчас можно» —
  `sendStrict()`: проверяет применимость к текущему снапшоту и
  возвращает `Rejected(expected: [...])` (для UI клиента: «форма уже
  отправлена»). Проверка — оптимистичная; окончательный результат — шаг.
- `defer: [event]` в состоянии — событие ждёт в inbox, пока конфигурация
  его не примет (UML deferred events), с TTL.

### 5. Таймеры

| Вид | Объявление | Отсчёт |
|---|---|---|
| относительный | `after: 'P3D'` / `after: '$.context.sla.reviewDuration'` | от входа в состояние |
| абсолютный (дедлайн) | `at: '$.context.deadline'` (ISO-8601) | момент времени |
| календарный | `after: businessDays(5)` | через интерфейс `BusinessCalendar` хоста (ядро не знает праздников) |

- Таймер — строка `pe_timers` с ключом `timer:<state>@<activation>:<id>`;
  создаётся командой шага при входе, отменяется при выходе.
- Срабатывание: `TimerTicker` атомарно `pending → fired` и вставляет событие
  `after.<id>` в inbox с тем же ключом → двойной тик безопасен.
- Устаревший таймер (активация уже другая) отбрасывается шагом —
  защита от гонки «отмена vs срабатывание».
- Время — через интерфейс ядра `Clock` (ADR-003); в тестах — виртуальные часы
  с `advance('P3D')`.
- Точность: минута при `schedule:run`, секунды с демоном `work`. Таймеры
  — для бизнес-сроков (часы/дни/недели), не для миллисекунд.
- **Просроченные таймеры** (`fire_at < now - grace` и всё ещё `pending`)
  — метрика здоровья: значит, тикер не работает.

### 6. Опрос внешней стороны — `poll` (G1)

Многие стороны не умеют присылать ответ сами (сервис подписи, учётная
система страховщика), их можно только спрашивать.

```php
->poll(CheckSignRequest::class, every: '1 minute')            // or every: $this->pollInterval(...)
```

- Опрос — деятельность состояния (как `invoke`): стартует при входе,
  останавливается при выходе. Технически это повторяющийся таймер
  (`pe_timers.repeat`) и эффект, который переиспользует одну строку
  `pe_effects` (`kind: poll`, счётчик попыток, `last_polled_at`).
- Обработчик обязан быть `#[Idempotent]` — иначе ошибка валидации.
- Результат обработчика:
  - `null` — ответа ещё нет. События нет, **журнал не пишется**, обновляются
    только счётчики. Это главное отличие от `after` + самоперехода, которые
    дали бы 1440 записей журнала в сутки;
  - событие (объект или имя) или список событий — доставляются в inbox
    экземпляра с ключом `poll:<activation>:<n>`;
  - `Publish`/`Send` — события другим экземплярам (§7).
- Интервал — строка или метод процесса (чистый, читает контекст), он
  вычисляется при каждом перепланировании. Адаптивный опрос («5 минут,
  если клиент недавно заходил, иначе час») — это метод, который читает
  поле контекста, обновляемое событием клиента.
- Немедленный опрос: `->on('client.opened-cabinet', run: CheckX::class)` —
  внеочередной вызов того же обработчика; плановый тик сдвигается.
- Ошибки опроса считаются по политике повторов эффекта. По исчерпании
  открывается инцидент, а опрос продолжается с максимальным интервалом.
  Внешняя сторона могла просто лежать, процесс не должен из-за этого
  умирать.
- `until:` (необязательно) — предел опроса. Чаще его заменяет обычный
  `after` на том же состоянии.

### 7. Эффект адресует события другим экземплярам (G7)

Эффект или опрос может вернуть `Publish::to($correlationKey, $event)` или
`Send::to($instanceId, $event)` (можно списком, вперемешку с собственными
событиями). Движок записывает их в транзакции фиксации результата
эффекта (txn B, ADR-004): `publish` проходит через подписки и буфер, `send`
попадает прямо в inbox адресата. Ключи идемпотентности выводятся из ключа
эффекта и номера элемента, так что повтор эффекта не задвоит события.

Пример: один опрос «все дела клиента» на заявление раздаёт статусы
дочерним процессам по номеру дела. Запросов к внешней системе становится
на порядок меньше, чем при опросе каждого дела.

## Последствия

- Внешние вебхуки хоста превращаются в `publish`/`send` в одну строку;
  повторная доставка вебхука безопасна.
- Буфер сообщений требует чистки по TTL (`tick`).

## Отвергнутые альтернативы

- **Отклонять событие, которое сейчас не ждут, ошибкой отправителю.**
  Для асинхронных сторон это превращает гонку в потерю ответа.
- **Таймеры отложенными джобами очереди.** См. ADR-004.
