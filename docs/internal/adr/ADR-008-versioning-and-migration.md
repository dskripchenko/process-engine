# ADR-008. Версионирование определений и миграция экземпляров

- Статус: принято автором 2026-10-26
- Дата: 2026-10-26

## Контекст

R5: экземпляры, запущенные на старой версии схемы, доходят до конца на ней;
нужен путь миграции, хотя бы описанный. Процессы живут неделями —
одновременно активны несколько версий.

## Решение

### 1. Версия неизменяема

- Определение идентифицируется `(name, version)`; при регистрации
  вычисляется `hash` канонической формы (нормализованный JSON, ключи
  отсортированы, `meta` входит — она видна во flow).
- В `pe_definitions` строка создаётся при первой регистрации.
  Повторная регистрация с тем же `hash` — no-op; с другим — **ошибка**
  `DefinitionVersionConflict` («изменили граф — поднимите версию»).
  В dev-окружении можно разрешить перезапись версии, у которой нет
  экземпляров (`allow_redefine_unused`).
- Новый экземпляр по умолчанию стартует на **последней** версии;
  можно явно указать версию.

### 2. Экземпляр привязан к версии навсегда (пока не мигрирован)

`pe_instances.definition_id` → конкретная строка `pe_definitions`. Рантайм
исполняет **сохранённую** каноническую форму. PHP-класс DSL старой версии
можно удалить из кода — процесс доживёт.

Что обязано оставаться в коде: **реализации по имени** (guards, эффекты,
сверки, компенсации), на которые ссылаются активные версии.

- Правило совместимости обработчиков: изменение, меняющее контракт
  (вход/выход/семантику) — новое имя (`payment.charge.v2`), старое живёт,
  пока есть экземпляры старых версий.
- `process-engine:doctor`: для каждой версии с активными экземплярами —
  разрешимы ли все имена; число экземпляров по версиям; версии без
  экземпляров (кандидаты на удаление обработчиков).
- Отсутствующий обработчик при исполнении — инцидент `handler_missing`,
  экземпляр ждёт (не падает).

### 3. Миграция экземпляра на новую версию

Явная, адресная, журналируемая операция — не автоматическая.

```php
Migration::from('claim-settlement', 2)->to(3)
    ->mapState('review.waiting', 'review.awaiting-party')   // переименование
    ->mapState('review.extra-docs', 'review.awaiting-documents')
    ->dropState('legacy.fax')            // экземпляры в нём не мигрируются
    ->context(fn (array $ctx) => [...$ctx, 'requests' => count($ctx['docRequests'] ?? [])])
    ->when(fn (InstanceView $i) => $i->openIncidents() === 0);
```

Миграция — PHP-класс в коде приложения: она исполняется один раз
оператором и не хранится как часть определения, поэтому замыкания в ней
допустимы.

Порядок:
1. **dry-run** (по умолчанию): для выборки экземпляров отчёт — мигрируем /
   нет и почему (состояние без отображения, эффекты в полёте, инциденты).
2. **Требование покоя:** нет `running`/`unknown` эффектов и открытых
   инцидентов; экземпляр под арендой мигратора.
3. Применение: новая конфигурация по отображению (несопоставленный
   атомарный → отказ), контекст через трансформер, **таймеры и подписки
   пересоздаются** по новым состояниям (`after` отсчитывается от момента
   миграции или сохраняет исходный срок — опция `preserveTimers`),
   `pending`-эффекты старой активации отменяются и, если новое состояние
   их объявляет, планируются заново. **entry-действия при миграции не
   выполняются** — это не вход в состояние, а перенос.
4. Запись журнала `migrated {from, to, stateMap, context_patch, actor, reason}`.

Массовая миграция — команда `process-engine:migrate {migration} --dry-run
--apply --where=…` пачками.

### 4. Совместимые правки без новой версии

Нет. Любое изменение канонической формы = новая версия. Изменения только
реализаций (обработчиков) без смены контракта — не требуют версии.

### 5. Усыновление — экземпляр сразу в заданном состоянии (G8)

Для перевода живых процессов со старого кода на движок и для сущностей,
заведённых во внешней системе мимо процесса:

```php
Processes::adopt(ClaimCase::class, in: ['awaitingDocuments'], context: $ctx,
    key: "claim:{$isn}", by: Actor::operator($user), reason: 'migration from legacy incidents');
```

- Конфигурация задаётся явно (атомарные состояния, для параллельных — по
  одному на регион) и проверяется на допустимость.
- **entry-действия не выполняются** (как при миграции): процесс уже был в
  этом состоянии, просто вне движка. Инфраструктура состояний создаётся:
  таймеры `after` (отсчёт от момента усыновления или от переданного
  `enteredAt`), подписки корреляции, опросы, `spawn`-области.
- Запись журнала `adopted {configuration, context, actor, reason}`.
- `key` делает операцию идемпотентной: массовый перенос можно
  перезапускать.
- Команда `process-engine:adopt` в Laravel-слое — пачками из
  пользовательского источника (callable, отдающий `[in, context, key]`),
  с `--dry-run`.

## Последствия

- В `pe_definitions` копятся версии; удалять можно только версии без
  экземпляров (команда `prune --definitions`).
- Flow рисует экземпляр по **его** версии определения — старые экземпляры
  показываются на старом графе (ADR-012).

## Отвергнутые альтернативы

- **Автомиграция всех экземпляров на последнюю версию.** Нарушает R5.
- **Версионирование кодом (patch-ветки в обработчиках, как Temporal).**
  Ветки живут годами; граф не отражает реальность.
