# ADR-011. Журнал, наблюдаемость, ручные операции

- Статус: принято автором 2026-10-26
- Дата: 2026-10-26

## Контекст

R6: журнал по экземпляру — аудит, «где сейчас», «почему здесь», история
переходов, кто и что ввёл. R7: текущее состояние, ожидающие события,
просроченные таймеры, ручные операции (повторить шаг, пропустить, отменить,
перевести в состояние) с записью в журнал.

## Решение

### 1. Журнал

Запись `pe_journal` пишется в транзакции шага/операции. Типы:

| Тип | Содержимое |
|---|---|
| `started` | версия определения, входной контекст, актор |
| `step` | событие (имя, ключ, payload после редактора), актор события, выбранные переходы (`source → target`, `event`, **какой guard дал true и какие кандидаты отклонены**), exited/entered, `context_patch` (RFC 6902), запланированные команды |
| `event.ignored` / `event.deferred` / `event.expired` | почему: конфигурация и список ожидаемых событий |
| `effect.started` / `effect.succeeded` / `effect.failed` / `effect.unknown` / `effect.reconciled` / `effect.orphaned` | ключ, попытка, результат/ошибка (усечённо) |
| `timer.fired` / `timer.discarded` | |
| `incident.opened` / `incident.resolved` | тип, решение |
| `manual.*` | операция, актор, **обязательная причина**, параметры |
| `migrated` | ADR-008 |
| `completed` / `failed` / `cancelled` | итог, `output` |

«Почему здесь» = последняя запись `step`/`manual.*`, приведшая в текущее
состояние, с guard-трассой. «Кто что ввёл» = `actor` + payload событий
(хранятся целиком, ADR-005).

Актор — значение-объект `Actor(type: user|system|party|timer|operator, id,
display?)`; ядро его не интерпретирует.

### 2. Запросы (read-модель ядра)

`ProcessQuery` (интерфейс в ядре, реализации в хранилищах):

- `instance(id)`: `InstanceView` — версия, статус, конфигурация (дерево
  активных состояний с временем входа), контекст, **ожидаемые события**
  (вычисляются по определению: все события, на которые есть переход из
  активной конфигурации; плюс подписки по корреляции и deferred). Guards
  **вычисляются сразу**, если зависят только от контекста: такое событие
  либо `available`, либо не попадает в список. Guards, которым нужны данные
  события (метод с параметром события или предикат по `$.event`),
  помечают событие как `conditional` — исход станет известен при отправке.
  Вычисление чистое (ADR-002), поэтому делать его на каждый запрос
  интерфейса безопасно, активные таймеры с `fire_at`, эффекты в полёте /
  `unknown`, открытые инциденты, дети.
- `journal(id, filters, cursor)` (для архивных — из `pe_archive.document`).
- Списки: по статусу, по определению/версии, по текущему состоянию, по
  `business_key`, «с инцидентами», «застрявшие» (нет активности N дней в
  неконечном состоянии без таймеров), «просроченные таймеры».
- Агрегаты по определению: число экземпляров в каждом состоянии — для
  обзорного снапшота flow (ADR-012).

### 2а. Клиентская проекция (G9)

Интерфейс клиента (кабинет) строится из того же `InstanceView`, без своих
статусных словарей и флагов:

- `label()` — `meta.label` самого глубокого активного состояния (для
  параллельных и дочерних — список);
- `expects()` — доступные сейчас события с `label` переходов: кнопки
  «Подписать соглашение», «Отказаться», «Загрузить документы»;
- `children()` — дочерние процессы (выплатные дела, запросы) со своими
  `label()` и `expects()`.

### 2б. Привязка к модели хоста (Laravel-слой)

Хосту нужно «найти заявки в статусе X» и показать статус в списке
привычными средствами Eloquent.

- `Processes::start(ClaimSettlement::class, $ctx, subject: $claim)` — экземпляр
  привязан к модели (`subject_type`/`subject_id`, ADR-005). У модели может
  быть несколько процессов (разных определений).
- Трейт `HasProcesses`:
  - `$claim->process(ClaimSettlement::class)` — `InstanceView`;
  - `$claim->processes()` — связь;
  - scopes `Claim::whereProcessIn('awaitingDocuments')`,
    `whereProcessNotIn(...)`, `whereProcessStatus('active')` (через
    `pe_active_states`, индексируемо).
- **Проекция в колонку** (необязательно): в классе процесса объявляется
  `project(Claim::class, 'status', using: ClaimStatus::class, map: [...])` —
  в той же транзакции, что и шаг, движок пишет в колонку модели значение
  по текущему состоянию (enum-cast поддерживается). Колонка — только для
  чтения со стороны хоста; источник истины — экземпляр. Дальше работают
  обычные индексы, сортировки, фильтры админки и чужой код, который
  смотрит на `status`.

### 3. Ручные операции

Все проходят **через inbox** как служебные события (`manual.*`) — значит,
сериализуются с обычными событиями под той же арендой и попадают в журнал
единообразно. Каждая требует `Actor` и `reason`.

| Операция | Действие |
|---|---|
| `retryEffect(effectId)` | `failed`/исчерпанный → `pending`, счётчик попыток с нуля; для `unknown` at-most-once — только с флагом `confirmUnsafe: true` (оператор берёт ответственность) |
| `resolveEffect(effectId, succeeded(result) \| failed(code))` | закрыть эффект вручную (в т. ч. `unknown` после внешней проверки); процесс получает обычное `done`/`error` |
| `skipEffect(effectId, result?)` | считать выполненным без выполнения (частный случай resolve с пометкой `skipped`) |
| `sendEvent(event)` | отправить событие от имени оператора |
| `transitionTo(target[], options)` | **перевод в состояние**: выход из текущей конфигурации (exit-действия — опция `runExitActions`, по умолчанию да), вход в целевую (entry — по умолчанию да), guards не проверяются; эффекты старой активации отменяются по ADR-006 §8 |
| `patchContext(patch)` | RFC 6902 к контексту; в журнал — патч |
| `suspend()` / `resume()` | приостановка: события копятся в inbox, таймеры при срабатывании ждут (не теряются), эффекты не стартуют |
| `cancel(compensate: bool)` | завершение экземпляра (детей — каскадно), опционально с компенсацией |
| `resolveIncident(id, resolution)` | закрыть инцидент (обычно вместе с одной из операций выше) |
| `migrate(...)` | ADR-008 |

Права — забота хоста (Laravel-слой даёт Gate-хуки `process-engine.manual.<op>`).

### 4. Сигналы наблюдаемости

- События ядра через свой интерфейс `EventListener` (ADR-003): `InstanceStarted`, `StepCommitted`, `EventIgnored`,
  `EffectSucceeded/Failed/Unknown`, `IncidentOpened/Resolved`,
  `InstanceCompleted/Failed/Cancelled`, `TimerOverdue`. Laravel-слой
  пробрасывает в свой диспетчер — подписываются метрики/алерты хоста.
- Команда `process-engine:status`: экземпляры по статусам, открытые
  инциденты, просроченные таймеры, зависшие аренды, глубина inbox —
  для health-проверок (интеграция с laravel-admin-health позже).
- OpenTelemetry — не в v1; точки (шаг, эффект) спроектированы так, чтобы
  обернуть их спанами без изменения API.

## Последствия

- Экраны админки (этап 10) строятся поверх `ProcessQuery` и ручных
  операций — ядру ничего не добавлять.
- Обязательная причина ручных операций — сознательное трение.

## Отвергнутые альтернативы

- **Ручные операции прямыми UPDATE мимо inbox.** Гонка с обрабатываемым
  шагом, разнобой в журнале.
