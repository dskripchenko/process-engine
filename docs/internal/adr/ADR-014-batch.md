# ADR-014. Пакетный вызов: этап по большому числу элементов

- Статус: принято автором 2026-10-27
- Дата: 2026-10-27

## Контекст

Конвейеры данных (обогащение объектов, загрузка регионов, проверка прокси) —
это этап, который обрабатывает **от сотен до миллиона элементов**, у каждого
элемента свой исход (готово, не найдено, ошибка), упавшие элементы
повторяются, внешние сервисы ограничивают скорость, а оператор видит прогресс
и счётчики. Первый потребитель — insurance-map, переносящий свой оркестратор
(`docs/process-engine-migration.md` там же).

`invoke(forEach:)` (ADR-009) для этого не подходит: список элементов живёт в
контексте (предел 256 КБ), все строки эффектов создаются в одном шаге и
каждая копирует контекст, выбор следующего при `concurrency` перебирает все
ожидающие эффекты экземпляра (O(N²)), результаты копятся в снапшоте, а один
упавший элемент валит весь вызов. Он остаётся для «десятков вызовов с
результатом каждого» — пакетный вызов не заменяет его.

## Решение

### 1. Объявление

```php
$p->state('dadata', fn (Builder $s) => $s
    ->batch(DadataLookup::class, items: ObjectsToEnrich::class, chunk: 50, concurrency: 2,
        itemAttempts: 3, into: 'counters.dadata', onDone: 'nspd', onError: ['fatal' => 'nspd', '*' => 'failed']));
```

- `items:` — класс-источник `ItemSource`; элементы **не** хранятся в контексте.
- обработчик (первый аргумент) — класс `BatchHandler`, обязательно
  `#[Idempotent]` (повтор пачки повторяет её элементы; `#[AtMostOnce]` для
  пакета отклоняется при сборке определения).
- `chunk` — элементов в одной пачке (одном вызове обработчика), по умолчанию
  100; `concurrency` — пачек одновременно, по умолчанию 1; `itemAttempts` —
  попыток на элемент, по умолчанию 3; `retry:` — политика повтора пачки, как
  у эффекта.
- `onDone`/`onError`/`into` — как у `invoke`; событие
  `done.invoke.<id>` несёт в `output` счётчики.

Каноническая форма: элемент `invoke` с ключами
`{id, batch: <handler>, items: <source>, chunk, concurrency, itemAttempts, retry?}`.

### 2. Контракты

```php
interface ItemSource
{
    /** Следующая страница ключей строго после $after в своём порядке; [] — источник исчерпан. */
    public function keys(mixed $context, ?string $after, int $limit): array; // list<string|int>

    /** Сколько элементов будет всего — для прогресса; null — неизвестно. */
    public function count(mixed $context): ?int;
}

interface BatchHandler
{
    /** @param list<string> $keys */
    public function handle(mixed $context, array $keys, Effect $fx): BatchResult;
}

BatchResult::of(['k1' => ItemOutcome::done(), 'k2' => ItemOutcome::notFound(), 'k3' => ItemOutcome::failed('timeout')]);
// ItemOutcome: done | notFound | skipped | failed(reason) | deferred(reason)
```

Аргументы `keys()`/`handle()` подставляются по типу, как у эффектов (контекст
объектом или массивом, сервисы — через контейнер в конструкторе). Ключ,
которого нет в результате, считается `failed('no outcome')`.

### 3. Исход пачки

| Обработчик пачки… | Результат |
|---|---|
| вернул `BatchResult` | исходы элементов записаны; `failed` — повтор элемента в следующих пачках, пока не кончится `itemAttempts`, затем окончательно `failed` |
| бросил `EffectNotExecuted` (временная недоступность, квота) | пачка повторяется целиком по политике с нарастающей паузой; этап **ждёт**, не падает |
| бросил другое исключение (неоднозначно) | как `EffectNotExecuted` — обработчик идемпотентен |
| исчерпал повторы пачки | каждому её элементу засчитывается попытка (`failed('retries exhausted: …')` либо обратно в очередь); пакет продолжается |
| бросил `EffectFailed($code)` | **пакет останавливается**: необработанные элементы → `deferred`, ожидающие пачки отменяются, событие `error.invoke.<id>` с кодом и счётчиками |

Так выражается прежняя семантика оркестратора insurance-map: ошибка элемента
не мешает остальным, временная недоступность ставит этап на паузу, фатальная
ошибка (нет ключа, баланс, бан) останавливает этап и даёт процессу решить, что
дальше (ADR-015 — выключение этапа).

### 4. Исполнение

Хранилище (отдельный контракт `BatchStore`, реализуют `InMemoryStore` и
`DatabaseStore`; без него определение с пакетом не запускается — инцидент
`handler_missing`):

- `batches`: `id, instance_id, key (ключ вызова), invoke, state, activation,
  handler, source, chunk, concurrency, item_attempts, retry, context (снимок
  контекста на входе), cursor, exhausted, status (running | done | failed |
  cancelled), counters, total, seq, created_at, finished_at`;
- `batch_items`: `batch_id, key, status (pending | queued | done | not_found |
  failed | deferred | skipped), attempts, reason, effect_id, updated_at`;
  уникальность `(batch_id, key)`, индекс `(batch_id, status, key)`.

Пачка — обычная строка эффекта вида `batch` (аренда, таймаут попытки, повторы,
`expiredEffects` тикера — общие), во `input` — id пакета и ключи пачки, без
копии контекста (обработчик получает снимок контекста пакета).

**Подкачка** (`refill`) — одна функция рантайма, вызывается в транзакции:
1. пока идущих пачек меньше `concurrency`: взять до `chunk` элементов
   `pending` по порядку ключа; если их меньше `chunk` и источник не исчерпан —
   запросить у источника следующую страницу (`chunk × concurrency`), вставить
   элементы `pending`, сдвинуть курсор (пустая страница — `exhausted`);
   выбранные элементы → `queued` с id новой пачки; пачка — `pending`;
2. если идущих пачек нет, ожидающих элементов нет и источник исчерпан —
   пакет `done`, экземпляру доставляется `done.invoke.<id>` (ключ inbox
   `batch:<id>:done` — ровно один раз).

Запуск: вход в состояние создаёт запись пакета и одну «подкачивающую» пачку
без ключей; её исполнение — `refill`. Завершение пачки — одна транзакция:
исходы элементов, счётчики, пачка `succeeded`, `refill`. Параллельные
завершения пачек одного пакета сериализуются версией записи пакета (`seq`,
как fencing экземпляра в ADR-004): конфликт — повтор транзакции.

Подкачка не ставит новых пачек, пока экземпляр приостановлен (`suspend`);
`resume` добавляет подкачивающую пачку каждому идущему пакету экземпляра.
Выход из состояния (`CANCEL_ACTIVATION`) отменяет пакет: ожидающие пачки
`cancelled`, элементы `pending`/`queued` → `deferred`, пакет `cancelled`;
идущие пачки дописывают исходы, но не подкачивают.

### 5. Масштаб

Цель — 1 млн элементов в пакете без деградации: каждая выборка — по индексу с
пределом, полных проходов нет; контекст в пачки не копируется; снапшот
экземпляра пакетом не растёт (в нём только ключ вызова); источник читается
страницами по курсору. Нагрузочный тест моста на PostgreSQL: 1 млн элементов,
`chunk` 500, `concurrency` 8.

### 6. Операции и наблюдаемость

- `Engine::batches($instanceId)`, `Engine::batchItems($batchId, $status, $after, $limit)` — для экранов.
- `Engine::retryBatchItems($batchId, statuses: ['failed', 'deferred'], Actor, reason)` — только у идущего пакета: элементы → `pending`, попытки обнулены, `refill`.
- `Engine::skipBatch($batchId, Actor, reason)` — оставшиеся → `skipped`, пакет `done` (в `output` — `skipped: true`).
- Журнал: `batch.started`, `batch.done|failed|cancelled` (со счётчиками), операции — с актором и причиной. Исходы отдельных элементов в журнал **не** пишутся (миллион строк) — они в `batch_items`.
- `InstanceView` содержит пакеты; `FlowExporter::snapshot` ставит на узел состояния значок прогресса («12 340 / 50 000», ошибки — `message`).
- Сигналы: `batch.started`, `batch.done`, `batch.failed`.

Повторить упавшие элементы **завершённого** пакета нельзя — процесс уже ушёл
из состояния; это делается новым запуском процесса по этим элементам (или
`transitionTo` обратно в состояние — новый пакет с нуля).

## Последствия

- Новый контракт хранилища `BatchStore` и две таблицы моста; `Store` не меняется (обратная совместимость 1.x).
- Харнесс падений расширяется точками в подкачке и завершении пачки; инварианты: каждый элемент обработан хотя бы раз, счётчики равны сумме по элементам, `done` пакета доставлен ровно один раз.
- `forEach` не меняется.
