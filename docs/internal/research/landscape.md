# Обзор подходов и готовых решений

Этап 0. Дата: 2026-10-26. Цель — понять, что брать из существующих систем,
что сознательно не брать и почему не взять готовое целиком.

Требования, по которым сравниваем (из постановки):

| # | Требование | Коротко |
|---|---|---|
| R1 | Граф состояний, guards, entry/exit/transition actions, иерархия, параллельность all/any | модель |
| R2 | Сон до события / таймера, состояние не в памяти | долгоживущесть |
| R3 | Снапшот после шага, подъём после падения, блокировки, идемпотентность | надёжность |
| R4 | Явная семантика повтора: повторяемое / неповторяемое (+«неизвестно») / компенсируемое; политики | эффекты |
| R5 | Старые экземпляры доживают на старой версии; путь миграции | версии |
| R6 | Журнал: аудит, «где», «почему», кто что ввёл | журнал |
| R7 | Наблюдаемость, ручные операции (повтор, пропуск, отмена, перевод в состояние) | управление |
| R8 | Ядро без предметной области | чистота |
| E1 | Определение и состояние рисуются @dskripchenko/flow без адаптера или с тонким | экосистема |
| E2 | PHP 8.2–8.5, Laravel 11/12/13, без внешней инфраструктуры сверх БД и очереди | экосистема |

## Temporal (durable execution)

**Модель.** Workflow — обычный код (в PHP — класс с генераторами `yield`),
состояние восстанавливается **воспроизведением** истории событий: код
перезапускается с начала, вызовы активностей и таймеров отвечаются из истории.
Activities — побочные эффекты с retry policy (initialInterval,
backoffCoefficient, maximumInterval, maximumAttempts, nonRetryableErrorTypes),
таймауты schedule-to-start / start-to-close / heartbeat. Signals и updates —
внешние события; queries — чтение состояния.

**Сильное.** Лучшая в индустрии проработка надёжности: history как источник
истины, детерминированные таймеры, retry policy как данные, heartbeat-ы
длинных активностей, идемпотентность через workflowId, child workflows,
continue-as-new для бесконечных процессов, saga-паттерн в SDK.

**Почему не берём готовым.**
- Инфраструктура: кластер Temporal Server (+ Cassandra/Postgres/Elastic),
  PHP-воркеры только под RoadRunner, клиенту нужен `ext-grpc`. Для экосистемы
  автора (Laravel-приложения, Octane, одна БД, очередь) это отдельный
  эксплуатационный контур.
- Детерминизм кода workflow и версионирование через `getVersion`/patching:
  для процессов на недели каждое изменение кода — ветка `if (version)` навсегда.
- **Граф неявен.** Процесс — это код; flow нечего рисовать без отдельного
  описания, «текущее положение» — это точка в коде, а не узел.
- **Ручной «перевод в состояние» (R7) в модели воспроизведения невозможен**
  по построению: нельзя переместить исполнение в середину функции. Temporal
  предлагает reset к событию истории — это откат, а не перевод.

**Берём.** Retry policy как данные и её поля; разделение «детерминированное
решение» / «побочный эффект»; идемпотентные ключи активностей; таймеры как
сохранённые объекты, а не `sleep`; child processes с собственной историей;
concept continue-as-new (как ограничение роста журнала — на потом).

## Durable Workflow (бывш. laravel-workflow)

Пакет `durable-workflow/workflow`: Temporal-подобная модель на очередях
Laravel и SQL-хранилище (таблицы экземпляров, логов для replay, сигналов,
таймеров, исключений). Workflow — код с `yield` как точками фиксации.

**Почему не берём.** Те же принципиальные возражения, что к Temporal: replay
кода, неявный граф (flow без адаптера не нарисует), нет перевода в состояние,
семантика «неизвестного исхода» не выделена. Плюс внешняя зависимость
с собственным темпом развития в центре движка автора.

**Берём.** Подтверждение, что durable-исполнение на SQL + очередях Laravel
жизнеспособно без отдельного сервера (наш стек исполнения такой же).

## Camunda 7 / Camunda 8 (Zeebe), BPMN 2.0

**Модель.** BPMN: токены по графу, user tasks, service tasks (external task
workers с fetch-and-lock), message correlation по correlation key с
**буферизацией сообщений по TTL** (Zeebe), boundary events (таймер/ошибка
на задаче), event-based gateway, parallel/inclusive gateways, call activity
(подпроцесс как отдельный экземпляр), **compensation**, **incidents**
(инцидент, когда retries=0 — оператор чинит и делает retry), process
instance migration с mapping инструкциями «старая активность → новая»,
модификация экземпляра (start before / cancel activity — по сути перевод).

**Почему не берём.**
- Camunda 8 — Java/Zeebe-кластер, Elastic/OpenSearch для Operate; у
  self-managed Camunda 8 лицензионные ограничения для продакшна. Camunda 7 CE
  снята с поддержки. Ни то ни другое не встраивается в Laravel-пакет.
- BPMN как формат определения тяжёл (XML, сотни элементов спецификации), а
  токенная семантика избыточна для «машины состояний с контекстом»: нам не
  нужны inclusive gateway с синхронизацией по токенам, компенсационные
  обработчики на ассоциациях и т. п.

**Берём.** Инциденты как объект первого класса; корреляция сообщений по
ключу и буферизация «ранних» сообщений с TTL; boundary-таймеры (у нас —
`after` на составном состоянии); fetch-and-lock для внешних исполнителей;
**migration plan как отображение состояний** + проверка применимости;
модификация экземпляра как штатная операция с журналом.

## AWS Step Functions (Amazon States Language)

**Модель.** JSON-автомат: Task, Choice, Wait (seconds/timestamp/path),
Parallel (все ветки), Map (по коллекции), Succeed/Fail. У каждого состояния
`Retry` (ErrorEquals, IntervalSeconds, MaxAttempts, BackoffRate, MaxDelay,
JitterStrategy) и `Catch` (ErrorEquals → Next). Callback-паттерн
`.waitForTaskToken`: задача отдаёт токен наружу и спит, пока внешняя сторона
не вызовет SendTaskSuccess/Failure с токеном; heartbeat. Executions до года.

**Почему не берём.** Vendor lock (AWS-only), не on-prem; нет иерархических
состояний и истории; нет ручного перевода в состояние; ограничения на
размер payload.

**Берём.** Декларативный JSON как канонический формат; `Retry`/`Catch` у
состояния с сопоставлением по коду ошибки; **task token** как модель «шаг
ждёт внешний ответ, адресованный по токену»; Map → multi-instance
подпроцессы; Wait с абсолютным временем из контекста (дедлайн).

## symfony/workflow

**Модель.** Workflow (сеть Петри: places, transitions, marking — в нескольких
местах сразу) и state_machine (одно место). Guards (через события и
ExpressionLanguage), события `guard/leave/transition/enter/entered/completed/
announce`, metadata, marking store в атрибуте объекта, дампер в Graphviz/
Mermaid/PlantUML.

**Почему не берём как основу.** Это библиотека «разрешённых переходов над
объектом», а не исполнитель: нет таймеров, ожидания событий, персистентного
исполнения, эффектов с retry, иерархии состояний, журнала. Тянет
symfony/* в ядро.

**Берём.** Чёткое разделение «определение графа» и «где сейчас объект»;
жизненный цикл событий перехода (leave → transition → enter) как точки
расширения; metadata у мест и переходов (у нас `meta`, идёт в экспорт).

## Laravel-пакеты state machine

- **spatie/laravel-model-states** — состояние как класс-значение атрибута
  модели, переходы классами, `canTransitionTo`. Хорошо для статуса заказа,
  но это атрибут модели: нет процесса, таймеров, ожиданий, журнала.
- **asantibanez/laravel-eloquent-state-machines** — состояние поля модели
  с историей переходов и отложенными переходами (pending transitions по
  времени). Близко к «журналу переходов поля», но нет иерархии, эффектов,
  идемпотентности.
- **sebdesign/laravel-state-machine** (winzou), **zerodahero/laravel-workflow**
  (обёртка symfony/workflow) — то же ограничение, что у symfony/workflow.
- **sassnowski/venture** — DAG джобов с зависимостями (workflow из jobs),
  без состояний, ожидания внешних событий и версий определений.

**Вывод.** Ни один не покрывает R2–R5 и R7. Берём идеи «история переходов
привязана к сущности» и «переход как объект с проверкой», не больше.

## XState / SCXML (statecharts)

**Модель.** Харелевские statecharts: атомарные, составные (иерархия, initial),
параллельные (регионы), финальные состояния, history (shallow/deep),
eventless (`always`) и отложенные (`after`) переходы, guards, actions
(entry/exit/transition), `assign` контекста, `invoke` (сервис/актор живёт,
пока активно состояние, результат — событиями `done`/`error`), `done.state.*`
событие при достижении финала составного/параллельного. Алгоритм SCXML
(W3C) формально задаёт порядок выбора переходов, выход/вход, микро- и
макрошаги. XState v5: актор-модель, persisted snapshots, сериализуемые
определения с действиями по имени (setup/implementations).

**Почему не берём готовым.** Это JS. Персистентное исполнение, inbox,
таймеры на недели, эффекты с семантикой повтора — вне его зоны
(snapshot-сериализация есть, durable-рантайма нет).

**Берём — как основу семантики (R1).**
- statechart как модель: иерархия, параллельные регионы, финалы, history,
  `always`, `after`, guards, entry/exit/transition actions;
- **детерминированный алгоритм шага SCXML** (выбор переходов, порядок
  exit/enter, микрошаги до стабилизации);
- `invoke` как «деятельность, привязанная к состоянию» с результатом
  событиями — это и есть мост к durable-эффектам;
- разделение определения (сериализуемо, действия по имени) и реализаций
  (код, регистрируемый по имени).

## Итог: что строим

Statechart-интерпретатор (семантика XState/SCXML) **с явным сериализуемым
графом** + durable-рантайм в духе Temporal/Step Functions (inbox/outbox,
таймеры и эффекты как сохранённые объекты, retry policy как данные) +
операционные идеи Camunda (инциденты, корреляция с буфером, migration plan,
модификация экземпляра).

Ключевой аргумент против всех готовых: требования R7 (перевод в состояние),
E1 (flow рисует определение и положение без адаптера) и «неизвестный исход
неповторяемого шага как отдельное состояние» вместе выполнимы только
в модели с **явным графом**, а единственные зрелые системы с явным графом
(Camunda, Step Functions) не встраиваются в Laravel-пакет.

Разбор решений — ADR-001…ADR-013 в [`../adr/`](../adr/).
